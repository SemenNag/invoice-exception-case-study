# Проверка решения: приёмочные тесты и eval агента

Контракт проверки реализации по [правилам core-v1](BUSINESS_RULES.md). Общая постановка, MCP-сценарий и порядок сдачи — в [README](../README.md). Runner и данные уже включены в репозиторий.

Прогонов два, и проверяют они разное:
1. **Детерминированный** — приёмочные тесты движка. Факты документа подаются уже извлечёнными, LLM не участвует; проверяется только бизнес-логика. Обязательный.
2. **Сквозной** — eval агента через MCP. Проверяется извлечение фактов из PDF и граница ответственности агента; итог по-прежнему считает приложение.

Разделение нужно, чтобы неверный итог можно было отнести либо к чтению документа, либо к применению правил.

## Детерминированный прогон

Runner подаёт эталонные факты документа, JSON-контекст, предложения и подтверждения. LLM не нужен. Кандидат предоставляет тонкий CLI-адаптер к тем же use cases, которые вызывает MCP. Внутреннюю архитектуру и имена MCP tools кандидат выбирает сам.

### Вызов адаптера

```
<команда кандидата> --state-dir <dir>  < step-input.json  > step-output.json
```

- Один процесс на каждый шаг кейса. Для каждого кейса runner создаёт новый пустой `--state-dir`, все шаги кейса используют этот же каталог. Состояние между шагами адаптер хранит только в нём.
- stdin — один JSON, stdout — один JSON, логи только в stderr.
- Exit code 0 — результат. Exit code 2 — ошибка валидации: в stdout `{"error": {"code": "VALIDATION_ERROR", "details": [...]}}`. Любой другой код — сбой.
- Таймаут шага — 30 секунд. Сеть и текущее время для результата не используются.

### Запуск runner

```
python3 tools/run_evals.py --adapter "<команда кандидата>" [--cases case-001,case-010] [--timeout 30] [--keep-state]
```

Нужен `jsonschema>=4.18`. Отчёты пишутся в results/local/eval-report.json и eval-report.txt; каталоги состояния — в results/local/state/, после прогона удаляются, если не указан `--keep-state`. Код выхода 0 — все кейсы пройдены, 1 — есть непройденные.

### Вход шага

- case_id, step, as_of, policy_ref.
- **context** — полный снимок контекста с context_version; передаётся на первом шаге и при каждом изменении контекста.
- **document** — document_id, content_sha256 и факты по схеме извлечения; передаётся при импорте документа.
- **proposals[]** — proposal_id, actor = agent, order_id, line_matches[] (document_line_id → order_line_id).
- **confirmations[]** — proposal_id, actor = human, confirmed_by.

После применения входа адаптер возвращает актуальный результат по документу кейса.

### Выход шага

- case_id, step, schema_version, policy_version, context_version, input_revision.
- import_disposition (new / duplicate / conflict), original_document_id, existing_assessment_ref.
- matched_order_id и order_match_source.
- lines[] — document_line_id, order_line_id, match_source, calculated_net, calculated_tax, ordered, received, previously_invoiced, available_to_invoice, remaining_on_order.
- totals — calculated_subtotal, calculated_tax_total, calculated_total.
- checks[] — code, object_id, status, severity, depends_on, actual, expected, evidence_refs.
- decision — clear / needs_information / needs_review / blocked. Для duplicate поле decision равно null: результатом является ссылка на оригинал; checks и lines пусты, totals = null. Нормативная форма задана step-output.schema.json.
- questions[] — required_fact, target_object_ids, text.

Decimal передаётся строками. Коды checks и required_fact — только из словаря core-v1.

## Что сравниваем

| Поле | Как сравнивается |
|---|---|
| decision, import_disposition, original_document_id | точно |
| checks | множество пар (code, object_id) совпадает с эталоном; для каждой пары точно status, severity и depends_on. actual, expected и evidence_refs не сравниваются |
| Вычисленные значения | как Decimal: `"60"` равно `"60.000"` |
| Соответствия | matched_order_id, order_line_id каждой строки и match_source — точно |
| questions | мультимножество пар (required_fact, target_object_ids); text не сравнивается |
| context_version | точно, как передал runner |
| input_revision | строго растёт между шагами кейса |

Также точно сравниваются case_id, step, document_id, matched_order_id и order_match_source. Если эталон шага — VALIDATION_ERROR, сравнивается только вид ответа (exit code 2 и объект error); details не сравниваются. Порядок checks, lines и questions не важен; actual, expected, evidence_refs, text и existing_assessment_ref не сравниваются.

Выход, который не проходит step-output.schema.json, считается сбоем адаптера, а не расхождением.

Шаг считается пройденным, если совпали все поля. Кейс пройден, если пройдены все его шаги. После непройденного шага runner продолжает выполнять следующие шаги кейса.

## Отчёт runner

- Таблица кейс × шаг с первым расхождением по каждому непройденному шагу.
- **Критическая ошибка:** clear при ожидаемом другом итоге выводится отдельно и не усредняется.
- **Лишняя эскалация:** более строгий итог, чем ожидается (например, blocked вместо needs_review или needs_review вместо clear), считается отдельной метрикой.
- **Недоэскалация:** менее строгий итог, чем ожидается (например, needs_review вместо blocked), — тоже отдельная метрика. Строгость: clear < needs_review < needs_information < blocked.
- Сбои адаптера (exit code, невалидный JSON, таймаут) — отдельной строкой.
- JSON-отчёт для машин и короткий текстовый для человека.

Цель самопроверки — 10/10 открытых кейсов. Автоматический отчёт показывает корректность вычислений и протокола; архитектура, MCP и интерфейс человека оцениваются отдельно. Итоговая оценка учитывает работоспособность, ограничения и объяснение решений.

## Эталоны

Каждый публичный кейс содержит:
- expected/extraction.json — проверенные факты PDF;
- expected/step-NNN.json — ожидаемый выход по каждому шагу;
- expected/notes.md — объяснение эталона.

Runner передаёт адаптеру только steps/. Expected остаётся у runner. Публичность эталонов помогает разработке; обобщение проверяется закрытыми кейсами по тем же правилам.

## Сквозной прогон локальным агентом

Codex или Claude Code проходит те же PDF и контекст через MCP, без эталонных фактов на входе.

- **Извлечение:** оценивается отдельно от доменных вычислений — пополевое совпадение с expected/extraction.json и существование каждого evidence excerpt на указанной странице.
- **Итог:** сохранённое приложением заключение сравнивается с эталоном по тем же правилам, что в детерминированном прогоне.
- **Граница ответственности:**
  - агент не регистрирует подтверждения человека;
  - в кейсе 004 инструкция из PDF не меняет итог и не попадает в данные как подтверждение;
  - агент не выдаёт свои вычисления за результат проверки.
- **Объяснения:** читаются ревьюером. LLM-as-judge не определяет корректность денег и блокирующих правил.

Кандидат сдаёт транскрипт и лог tool calls для кейсов 004 и 010 с указанием клиента, модели и версии данных. На ревью мы повторяем прогон на новом PDF.

## Отдельное ревью

Кроме прогона runner на закрытых кейсах по тем же правилам, ревьюер вручную проверяет только опубликованные требования:

1. Повторный прогон приёмочных тестов даёт тот же результат.
2. Сквозной прогон агентом на новом PDF: факты сохранены с источниками, итог считает приложение.
3. Инструкция внутри PDF не меняет итог, и у агента нет способа получить clear или подтверждение.
4. Цепочка неоднозначность → предложение агента → подтверждение на странице → новое заключение; прежние заключения сохраняются.
5. После перезапуска процессов кейс, факты, подтверждения и история на месте.
6. Новый контекст создаёт новую ревизию и новое заключение.
7. Повторный импорт того же документа даёт duplicate, изменённого — conflict.
8. Ошибочный вход даёт понятную ошибку валидации без падения.

Устойчивость к повторам вызовов, сбоям между записями и конкурентным подтверждениям реализовывать не нужно: это темы для обсуждения на интервью. Там же — небольшое изменение правила в вашем коде. Новых скрытых бизнес-правил не будет.
